# Task plan: Native OAuth callback bridge

## Summary

Build the mobile-side OAuth bridge needed for Google/passkey sign-in to run in the system browser/auth session instead of the embedded WebView. The app will request a server-owned mobile OAuth start URL, launch it with the native browser auth handoff, receive a custom-scheme callback, extract the OpenWebUI JWT, and feed it through the existing `loginWithApiKey(..., authType: 'sso')` path. Document the durable auth decisions with ADRs.

## Locked user decisions

- The app should default first-run users to `https://chat.publicai.co`; users should not see the server connection screen in the normal Public AI path.
- Google/passkey auth should move toward native browser/system auth rather than embedded WebView.
- The native app needs a callback bridge; do not rely on scraping system-browser cookies.
- Existing username/password, token, LDAP, WebView SSO fallback, and saved-session behavior should remain available unless the server/browser bridge succeeds.
- Do not log raw tokens, cookies, passkeys, authorization codes, or callback URLs containing credentials.

## PLAN

### Architecture contract

Client-side contract implemented in this repo:

- Callback scheme: `publicai`
- Callback URI: `publicai://auth/callback`
- Start URI builder:
  - Base server: active `ServerConfig.url`, normally `https://chat.publicai.co`
  - Path: `/api/mobile/oauth/start`
  - Query params:
    - `provider`: OAuth provider key from OpenWebUI config, e.g. `oidc` for the current PublicAI/Cognito-style deployment or `google` for a direct Google provider
    - `redirect_uri`: `publicai://auth/callback`
    - `state`: cryptographically random nonce generated by the app
- Callback parser accepts:
  - success, preferred: `publicai://auth/callback?code=<single-use-code>&state=<same-state>`
  - success, legacy/dev-only fallback: `publicai://auth/callback?token=<short-ttl-jwt>&state=<same-state>` only when explicitly enabled by a debug/test flag; production Android must not rely on token-in-custom-scheme because another app can register the same scheme.
  - failure: `publicai://auth/callback?error=<code>&error_description=<message>&state=<same-state>`
- The app rejects callbacks when:
  - scheme/host/path do not match
  - `state` is missing or mismatched
  - neither `code`, `token`, nor `error` is present
  - token is not JWT-shaped

Server-side bridge expected outside this repo:

PublicAI already has working website OAuth at `https://chat.publicai.co`. The server implementation should reuse that exact OpenWebUI/Cognito/OIDC flow and add only a minimal mobile handoff at the final redirect. Do not build a second Google/OIDC stack and do not point Cognito directly at the app.

1. Receive `/api/mobile/oauth/start` with provider, redirect URI, and state.
2. Validate provider and redirect URI, then set a short-lived signed HTTP-only mobile intent cookie containing provider, redirect URI, state, issued-at, and expiry.
3. Redirect into the existing OpenWebUI provider OAuth start path, normally `/oauth/{provider}/login`. For PublicAI, the provider key may be `oidc` even if the user-facing provider is Google.
4. Complete OAuth through the existing OpenWebUI callback path so provider verification, user provisioning, policy checks, OAuth session storage, and JWT minting remain centralized.
5. At the final success redirect decision point only, if the signed mobile intent cookie is valid for the same provider, create an opaque short-lived single-use Redis handoff code and redirect to `publicai://auth/callback?code=<single-use-code>&state=<state>`.
6. On error for a mobile-started flow, redirect to `publicai://auth/callback?error=<code>&error_description=<safe-message>&state=<state>` without leaking provider details.
7. Receive mobile exchange request at `/api/mobile/oauth/exchange` with `code`, `state`, and `redirect_uri`; atomically validate and consume the single-use code/state/redirect URI and return `{ "token": "<OpenWebUI JWT>" }` over HTTPS.
8. Preserve existing web OAuth behavior unchanged for flows that do not have a valid mobile intent cookie.

Out of scope for this mobile repo:

- Implementing the server endpoint in this mobile repo. The backend implementation plan lives at `ai/tasks/openwebui-mobile-oauth-server-bridge.md`.
- Changing Google Cloud OAuth client settings unless the existing OpenWebUI callback URL is not already authorized. Google should continue redirecting to the server callback, not directly to the mobile app.
- Universal links / app links in the current mobile code. Use custom scheme first because it is enough for TestFlight and avoids domain association setup; universal/app links are the planned hardening step once the server/mobile bridge contract is proven.

### Task 1: Add pure mobile OAuth bridge contract and tests

Objective: Create testable URI/state/token logic without platform dependencies.

Files:

- Create: `lib/core/auth/mobile_oauth_bridge.dart`
- Test: `test/core/auth/mobile_oauth_bridge_test.dart`

Implementation requirements:

- `MobileOAuthBridge.callbackScheme == 'publicai'`
- `MobileOAuthBridge.callbackUri == Uri(scheme: 'publicai', host: 'auth', path: '/callback')`
- `String createState()` returns a URL-safe random string, at least 32 chars, generated with `Random.secure()`.
- `Uri buildStartUri({required Uri serverUri, required String provider, required String state})`
- `MobileOAuthCallback parseCallback(Uri callback, {required String expectedState})`
- `MobileOAuthCallback` has success/error variants or equivalent fields: `code`, `token`, `error`, `errorDescription`.
- Do not print/log callback URLs in this pure layer.

Tests:

- start URI uses `/api/mobile/oauth/start` and includes provider, redirect_uri, state.
- parse success callback returns code.
- parse legacy/dev-only token callback returns token and validates JWT shape.
- parse rejects wrong scheme/host/path.
- parse rejects state mismatch.
- parse returns structured error for error callbacks.
- parse rejects non-JWT token.

### Task 2: Add native browser auth platform channel

Objective: Launch OAuth through native browser auth and return the callback URL to Dart.

Files:

- Create: `lib/core/auth/native_browser_auth.dart`
- Modify: `ios/Runner/AppDelegate.swift`
- Do not modify: `ios/Runner/Info.plist` for the ASWebAuthenticationSession callback scheme. `publicai` should not be added to iOS `CFBundleURLTypes` for this path because `ASWebAuthenticationSession` intercepts the callback using `callbackURLScheme`.
- Modify: `android/app/src/main/kotlin/ai/public/app/MainActivity.kt`
- Modify: `android/app/src/main/AndroidManifest.xml`
- Test: `test/core/auth/native_browser_auth_test.dart` if feasible with method-channel mocking.

Dart API:

```dart
class NativeBrowserAuth {
  static const MethodChannel _channel = MethodChannel('com.publicai.app/native_browser_auth');

  Future<Uri> authenticate({required Uri startUri, required String callbackScheme});
}
```

Dart behavior:

- Calls native method `authenticate` with `{url, callbackScheme}`.
- Native returns callback URL string.
- Dart parses it as `Uri` or throws `NativeBrowserAuthException`.
- Never logs full callback URL.

Native iOS behavior:

- Use `ASWebAuthenticationSession` with callback scheme `publicai`.
- Implement `ASWebAuthenticationPresentationContextProviding`.
- Resolve presentation anchor from the foreground connected `UIWindowScene` key window because this app uses scene configuration (`FlutterSceneDelegate`) rather than AppDelegate-owned windows. Fallback to the first visible connected scene window if no `isKeyWindow` is available; return a structured error if no anchor exists.
- Set `prefersEphemeralWebBrowserSession = false` so Safari/system Google/passkey session state can be reused.
- Return callback URL string on success.
- Return structured Flutter errors for cancel/no-callback/platform failures.
- Keep the session strongly referenced until completion.

Native Android behavior:

- Add an intent-filter to `MainActivity` for `publicai://auth/callback`.
- The intent filter must include `android.intent.category.BROWSABLE` and `android.intent.category.DEFAULT`, and constrain `scheme="publicai"`, `host="auth"`, and `path="/callback"`.
- Launch `Intent.ACTION_VIEW` for the start URL. This is system-browser handoff without adding a dependency; Custom Tabs can be a later improvement.
- Store one pending Flutter result for the in-flight auth attempt.
- Persist the pending auth state minimally in `SharedPreferences` before launch: `state`, `startedAtMillis`, and a boolean `pendingNativeOauth`. Clear it on success, cancel, or timeout.
- In `onNewIntent`, if the intent data matches `publicai://auth/callback`, complete the pending result with that URI.
- If the callback arrives after process death with no pending Flutter result, store the orphan callback URI in `SharedPreferences` under a short-lived key and expose a Dart `consumePendingCallback` method. Dart startup/auth page can consume it, validate state against persisted pending state, and either complete login or show fallback.
- Reject concurrent auth attempts.
- Return structured Flutter errors for invalid args/no browser/concurrent attempts.

### Task 3: Integrate native bridge into SSO auth flow

Objective: Prefer native browser auth for OAuth providers, with WebView fallback retained.

Files:

- Modify: `lib/features/auth/views/authentication_page.dart`
- Modify: `lib/features/auth/views/sso_auth_page.dart` only if existing WebView page needs clearer fallback copy.
- Test: targeted widget/unit tests if existing harness permits; otherwise pure service tests plus manual validation notes.

Behavior:

- `_buildOAuthButton(provider, l10n)` should trigger native browser auth first.
- Flow:
  1. Ensure server config is saved if needed, same as current `_navigateToSso`.
  2. Resolve active/current server URL.
  3. Generate state.
  4. Build start URI using `MobileOAuthBridge`.
  5. Call `NativeBrowserAuth.authenticate`.
  6. Parse callback with expected state.
  7. If callback has `code`, call `ApiService.exchangeMobileOAuthCode(code, state, redirectUri)` against `/api/mobile/oauth/exchange`.
  8. If exchange returns a token, call `authActions.loginWithApiKey(token, rememberCredentials: true, authType: 'sso')`.
  9. If callback has a token, accept it only when the explicit legacy/dev flag is enabled; otherwise reject with a safe error.
  10. If native launch, callback parsing, or exchange fails, show a clear error and offer existing WebView SSO fallback.
- Do not remove the embedded WebView route yet; it remains fallback for unsupported server bridge or platforms.
- Redact WebView SSO navigation logs while this fallback remains. Existing log lines must not print full URLs because OAuth pages can include authorization codes or provider state.
- Do not show server connection screen on normal Public AI startup.

## BETTER ENGINEERING INSIGHTS + BACKLOG ADDITIONS

- Universal links/app links are better than custom schemes for anti-hijack hardening, but they require domain association files and entitlement setup. Defer mobile code changes until the custom-scheme bridge proves the server/mobile contract; design the server redirect allowlist to support both `publicai://auth/callback` and future `https://chat.publicai.co/mobile/auth/callback`.
- Android Custom Tabs would be a better UX than raw `ACTION_VIEW`, but adding AndroidX Browser or a Flutter auth plugin should be a deliberate dependency decision. The first implementation can use the installed platform with no new package.
- The server bridge must avoid putting production long-lived tokens in custom-scheme URLs, especially on Android where another app can claim the same scheme. Use short-lived single-use codes plus HTTPS exchange as the production path.
- Since PublicAI controls the OpenWebUI instance and `chat.publicai.co` web OAuth already works, backend work should reuse the existing OpenWebUI/Cognito/OIDC flow and only add a signed mobile intent cookie plus Redis handoff-code branch at the final redirect.
- `ai/learnings.md` still references a root `AGENTS.md`, but this checkout does not currently have one. Do not block this auth feature on that doc cleanup; record as a repo-doc follow-up if needed.
